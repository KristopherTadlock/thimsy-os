# Thimsy: first-boot game launch failure

## Status and scope

This document proposes a fix for first-boot game-library initialization in Thimsy's Nano home using the ES-DE theme. It records the observed failure, the relevant source behavior, and how to establish whether the proposed fix resolves the device problem.

The configuration reload gaps described below are present in the inspected code. Their connection to the reported device failure remains a hypothesis: no first-boot device log has been captured. This document does not claim a confirmed root cause or an implemented fix.

Source inspected: `thimsy`, project commit `ff21313`, and the accompanying local Android source in `/home/michaeltadlock/gammaos-src`. The Android working tree contains local changes; the project commit alone does not identify every native source revision or prove what is in the flashed image.

## Reported problem

On the first boot after installation:

- Setup completes and the ES-DE-themed menu appears.
- Navigation works, including A presses used to enter menus.
- Selecting a game appears to do nothing.
- Rebooting makes game launch work.

Expected behavior: the first usable game menu must launch games in that same boot. Rebooting must not be a required setup step.

Working A presses make a general button failure or a modal consuming every A press unlikely. The investigation should follow the selected game through its configuration, launch checks, and emulator handoff.

## Which library files matter

The current default home is Nano's ES-DE theme engine. Its launch path uses:

- `/data/system/nano_systems.json`: system definitions, ROM folders, RetroArch cores, emulator packages, and launch intent templates.
- `/data/system/nano_xmb_cache/`: cached ROM lists, keyed by system ID.
- The running process's `mXmbSystems`: the system configuration and ROM lists used by the game menu and launch functions.

For RetroArch, Nano passes the selected ROM and core directly. `launchXmbGame()` builds the core path and publishes the launch request; `RootWindowContainer` supplies `ROM` and `LIBRETRO` activity extras to RetroArch. A RetroArch `.lpl` playlist is not required for this direct launch.

A library setup problem is therefore plausible, but the first files to investigate are Nano's system definitions and ROM caches. Regenerating RetroArch playlists would not repair an incorrect in-memory Nano emulator mapping.

## Current first-boot sequence

### 1. Nano loads an initial configuration before installation finishes

`initXmbSystems()` reads `/data/system/nano_systems.json`. If it cannot load a configuration, it seeds the built-in defaults. The process can therefore hold those defaults while first-boot setup is still installing this build's apps, cores, and game configuration.

The built-in mappings differ from this project's choices. For example:

- Built-in NES: `nestopia_libretro_android.so`; project NES: Mesen.
- Built-in Game Boy/Game Boy Color: Gambatte; project choices: SameBoy.
- Built-in GBA: gpSP; project choice: mGBA.

A valid ROM list can show the right game names while retaining the wrong emulator mapping. Actual core availability must be checked on the device before attributing a failure to one of these differences.

### 2. Setup replaces the configuration on disk

The first-boot steps generated by `mods/50-nano.sh` copy:

`/system/etc/gammaos/nano_systems.json` → `/data/system/nano_systems.json`

when `FRESH_SETUP=1`, then set its owner, mode, and SELinux label. That updates the file. It does not directly replace `mXmbSystems` in the already-running Nano process.

Reference: [fresh-setup configuration installation](/home/michaeltadlock/thimsy/mods/50-nano.sh:77).

### 3. Finishing setup requests a scan without explicitly reloading configuration

`finishSetupWizard()` refreshes installed apps, marks the XMB categories stale, and calls `forceRescanAllSystems()`.

`forceRescanAllSystems()` scans the current systems. It does not call `loadSystemsConfig()` or `initXmbSystems()`. A rescan and a configuration reload are different operations: scanning the old catalog can find games without adopting the newly installed core or package selections.

References:

- [setup completion](/home/michaeltadlock/gammaos-src/frameworks/base/cmds/gammaos-nano/NanoMenuSetupWizard.cpp:182)
- [background rescan entry point](/home/michaeltadlock/gammaos-src/frameworks/base/cmds/gammaos-nano/NanoMenuXmb.cpp:1934)

### 4. Automatic configuration reload depends on menu state

The main loop notices a changed configuration timestamp and reloads the systems, but that check is inside a block requiring an empty menu stack, no setup or relevant modal, and settled XMB animation state.

The animation predicate exempts DSi and Minima. It does not exempt ES-DE. Shared XMB animation flags can remain set when navigation returns to a renderer that does not finish those XMB animations. In that state, the block containing the configuration reload cannot run.

Setup completion does not establish that the new configuration has been adopted before exposing game launch. This leaves correctness dependent on a later eligible main-loop tick. Rebooting reads the on-disk configuration into a new process, which is consistent with the reported recovery.

Reference: [configuration reload and animation predicate](/home/michaeltadlock/gammaos-src/frameworks/base/cmds/gammaos-nano/NanoMenu.cpp:5913).

## What is still unproven

The sequence above establishes a way for configuration adoption to be delayed. It does not establish which launch branch failed on the device.

In particular:

- A missing RetroArch core normally produces an "emulator not installed" message. The report of no visible response needs explanation from the actual launch trace.
- A blocked boot-readiness check normally shows "Booting up...". No such message was reported.
- Some built-in and project mappings agree, including SNES. A stale catalog does not automatically explain failure of every game or emulator.
- Android provisioning, app-visible storage, and the launch trigger may have separate failures. The asynchronous final provisioning commands alone do not explain a persistent failure throughout the first boot.

Confirm the selected system ID, ROM path, core/package, adopted configuration version, and launch outcome before declaring the reload gap the root cause.

## Proposed solution

### A. Make configuration adoption an explicit setup-completion step

Replace the assumption that a rescan will pick up installed mappings with an explicit request to reload the completed game configuration and then rescan it.

Use a small pending operation serviced by the main loop, with visible progress. The required order is:

1. Confirm the setup service has finished and the required configuration file was installed successfully.
2. Request configuration reload before starting a new scan of the old catalog.
3. Allow any existing background scan to finish. Discard its pending results before replacing the catalog.
4. Load and validate the new configuration.
5. Replace the catalog on its owning thread.
6. Rescan ROM folders using the new definitions.
7. Apply the resulting ROM lists, rebuild the visible systems, and restore selection by stable system ID and ROM path.
8. Enable game launches from the adopted configuration.

Keep menu rendering responsive. Show "Preparing game library..." while the operation is pending, and allow menu navigation. A game-launch attempt during that interval must show that preparation is underway rather than disappear silently. If loading fails, present a useful error and retry action.

Do not clear and rebuild `mXmbSystems` while the current scan worker is accessing it. The existing worker reads the catalog, and pending results are indexed against that catalog. Replacing it concurrently or applying old results to new indices can associate games with the wrong system.

Use the existing scan completion protocol safely, with synchronized visibility of completion. Do not add a blocking wait or thread join to the input/render path. With the current detached worker, defer replacement until it is finished; a completion flag must actually mean no further catalog access will occur.

This setup-specific operation should run independently of the decorative XMB animation predicate. It must not wait indefinitely for a particular theme or menu stack to become idle.

### B. Correct the ES-DE animation exemption

Include `mEsdeTheme` in the predicate that already exempts DSi and Minima from XMB-specific animation completion. Retain appropriate protections against rebuilding visible lists in the middle of an actual view transition.

Separate detection of a configuration change from presentation work where practical. Record a pending reload even when a submenu is open; apply it through the safe catalog-replacement path when eligible. The first-boot request from step A must have a definite completion path.

This repairs ordinary reload behavior too, including returning from native settings screens to the ES-DE home. It is a small correction, but should accompany the explicit setup operation rather than serve as its only guarantee.

### C. Load this build's bundled defaults on a fresh device

When the persisted configuration is genuinely absent, prefer the valid bundled `/system/etc/gammaos/nano_systems.json` before falling back to hard-coded defaults. Persist the chosen initial catalog using the normal ownership and labeling rules.

This gives the first Nano process the build's intended mappings immediately. It reduces the period where the launcher and newly installed cores disagree.

Preserve existing user configurations. An unreadable or malformed existing file should produce a recoverable error, with no silent replacement of the user's settings. A bundled-file parse failure should be logged clearly. Hard-coded fallback remains a recovery option for a genuinely fresh device without a usable bundled catalog.

### D. Publish setup configuration atomically

Change the generated fresh-setup step to prepare a temporary file in `/data/system`, apply its owner, mode, and SELinux label, and rename it over the target only after preparation succeeds.

Check the operation's status and report failure to the setup UI. Do not announce successful configuration installation after a failed copy or rename. Keep the fresh-setup guard so updates and repeat setup do not replace user emulator choices.

Atomic publication prevents the live reader from seeing a truncated file during a copy. It complements explicit reload; it does not substitute for it.

## Launch diagnostics

Add concise diagnostics at configuration adoption and game launch, outside frame-by-frame render logging:

- Configuration source and version/stamp loaded, system count, and whether a reload is pending.
- Selected stable system ID, ROM path, launch type, core or package, and whether the selected mapping comes from the adopted configuration.
- Each rejected game launch, with its actual reason: library preparing, invalid selection, missing ROM, missing emulator, or boot/storage not ready.
- Launch-trigger publication, framework receipt, and the selected activity or command result.

Use a stable configuration generation or equivalent token for diagnostics and any pending launch. Resolve the selected game again after a catalog swap instead of retaining numeric indices into the previous catalog. Cancel a queued launch with a visible explanation if its game disappeared.

For the current build, capture the first-boot log immediately after selecting a game, before rebooting:

```bash
adb logcat -b all -d > first-boot-launch.log
```

Inspect these existing messages in sequence:

- `NanoMenu: select (...)`
- `nano_systems.json changed externally, reloading`
- `refusing to launch, emulator missing`
- `NanoMenu XMB: launching ... core=...`
- `do_launch detected, triggering relaunch`
- `direct game launch ROM=... CORE=...`

A published ROM/core request followed by no framework launch moves the investigation to the handoff. An emulator activity that starts and dies moves it to the emulator or storage. Neither outcome should be labeled a playlist failure without evidence.

## Verification and acceptance criteria

Use a fresh installation or factory-reset test device; restarting an already provisioned Nano process does not reproduce first-boot setup. Record the exact flashed build and retain its setup and launch logs.

1. Complete setup and launch a bundled game without rebooting.
2. Verify NES uses Mesen and Game Boy uses SameBoy on that first boot. Include SNES as a case whose built-in and project mappings agree.
3. Launch a game through a standalone emulator, such as PPSSPP, to cover the package/intent path as well as RetroArch.
4. Navigate into native settings and back while setup results are being adopted. Confirm reload completes in ES-DE even with stale XMB animation flags.
5. Complete setup with a scan already running. Confirm old scan results cannot overwrite the new catalog or attach to a different system index.
6. Select a game during library preparation. Confirm visible feedback and correct launch or explicit cancellation after preparation.
7. Simulate a missing core and invalid configuration. Confirm useful errors and preservation of user configuration; no silent failure or destructive reseeding.
8. Repeat setup and reboot. Confirm emulator choices, ROMs, saves, and states are preserved and launches still work.

For implementation verification, exercise the configuration replacement and old-scan-result rejection as meaningful regression cases. Then verify the actual emulator activity, resolved ROM/core, and rendered gameplay on hardware. A source build alone is not acceptance.

Success means first-boot launches work, the runtime mappings match the installed configuration, reload does not depend on reboot or theme switching, and failed launches explain their reason.
