# Per-device config plan: emulator sets per device, the theme on the card

Status: draft for review (2026-11-27), revised after the first review. Nothing here is built or run. It designs the owner's rethink of config portability (`docs/linux/DECISIONS.md` OA-46 to OA-54) for both builds. Revised the same day for OA-46's wording (`systems.json`'s launch fields) and for OA-52 to OA-54 (shared emulator storage; shared saves, states and BIOS; emulator definitions), then after the second review: saves live in a fixed folder per save family, so no change of picks or launch fields can move or hide one (§2.7), and per-launch keys never stay in a stored file (§5.6); then after the third review: a save made outside those folders (beside the ROM, loose, or by RetroArch started outside Nano) is taken in per game or listed, never hidden, the slot keeps the shipped values between launches, shared storage stays internal while `emu_sd` is off, and a real folder is merged before a link replaces it (§2.7, §5.6); then after the fourth review: Nano's launch-only RetroArch values go only into a per-launch copy of its config that no other launcher reads, Linux strips its append keys from the live file after a run (§5.6), and two games of one name in two subfolders of a system keep two saves (`{subdir}`, §2.7), and no swept or kept save is overwritten, or swept after another device has used the card (§2.7, §5.6). Line numbers are at `linux` 9cdec1c. Facts not checked on a device or in a tool's source are marked **(verify)**; estimates are marked *(guess)*.

## Requirement (owner, 2026-11-27)

- **OA-46:** emulator settings (RetroArch, PPSSPP, ScummVM and the rest of `emulator_config/`) and the launch configuration (which emulator, core or app launches each platform/system and each game, including the launch fields `systems.json` holds for each platform) are per device. One card holds several devices' sets side by side. Thimsy uses the card's set for this device, else the device's local set. A per-device "SD card settings" switch: turning it on copies the local set to the card; when it is on and the card has no set for this device, the local set is copied to the card. The device always keeps a local mirror; with the switch on, the card's set wins and refreshes the mirror, and device changes go to both. A set is keyed by the unit's chip serial and the platform (coordinator, for audit).
- **OA-47:** Thimsy's own settings are local only. No `settings.ini`. `prefs.json` stays as the inventory. OA-35's seeding stays.
- **OA-48:** music playlists on the card (`Thimsy/playlists/<name>.m3u8`), no device mirror, card wins. `nano_music.json` becomes a scan cache.
- **OA-49:** box art, media, gamelists and collections on the card only, no mirror.
- **OA-50:** PortMaster and everything it installs is local.
- **OA-51:** the theme switches (XMB, ES-DE, Minima and the like, with their style switches) and each theme's settings are on the card, shared by every device, card first; the local value is used with no card. Aspect ratio stays local (coordinator). Where on the card it lives is settled here (§2.4).
- **OA-52:** emulated system storage (Vita3K's `ux0`, Eden's NAND and SD, Dolphin's Wii NAND, Azahar's NAND and SD, PPSSPP's memory stick, PS2 memory cards) is shared on the card, the same for every device, with no device mirror. The emulator's settings stay per device. Where settings and storage share a folder, Thimsy keeps the settings per device and points the emulator at the shared storage (§2.7).
- **OA-53:** in-game saves, save states and BIOS files are on the card, shared by every device, with no device mirror. OA-21 still decides which files two cores can share; differing cores' files stay apart by name or folder, and a state is offered only to the core that made it (coordinator, for audit).
- **OA-54:** everything an emulator integration needs (the per-device set, the shared storage, the hotkeys, the controller map, the launch configuration, card or local storage) comes from emulator definition files, `user_emulators_plan.md`'s definition extended, on both builds. The shipped emulators use the same files. Not implemented now, and nothing built now may hard-code what a definition says (§2.8).

## Conventions

- **Set:** one device's emulator settings files and its launch configuration (picks).
- **Card set:** this device's set on the card, `emulator_config/devices/<id>/`.
- **Local set:** this device's set on its own storage. It is OA-46's mirror.
- **Live file:** the file an emulator actually reads (an Android app's private folder, a folder on the card the emulator was pointed at, or Linux's `/storage/.config/<emu>`).
- **Shared storage:** an emulator's files that are the same for every device: emulated system drives (OA-52), in-game saves, save states and BIOS (OA-53). On the card only, never in a set, never mirrored (§2.7).
- **Definition:** an emulator definition file (`user_emulators_plan.md` §1 and §1a). It says which of an emulator's files are settings, which are shared storage and which are left out, and how the emulator is launched and pointed at its files (§2.8).
- **Library card:** the card whose `ES-DE` folder Nano uses as the store (OA-25 chooses between two). The emulator sets use the card `usb_storage_plan.md` calls the Emulator Settings Drive where that setting exists, else the slot card (`emuSdSlotCard`, never a USB drive). On today's devices the two are the same card.
- **Theme card:** the card that holds `Thimsy/theme.json` (OA-51): the library card when the store is on a card, else the slot card (`emuSdSlotCard`). Store mode is opt-in on Android: it is off while `persist.gammaos.nano.esde.dir` is empty (`esdeStoreMode`, `NanoEsdeStore.cpp` 128-132), and the default store is internal (`/storage/emulated/0/ES-DE`, line 59). So a device with a card in and no store on it still has a theme card. On Linux it is the library card, which is always a card.
- **Parked set:** a local set that belongs to another id, kept beside the live one (§5.4).
- **AS** / **LO**: a step that changes Android-compiled code (an `android-surface:` commit, cherry-picked after the AOSP build), or one that touches only Linux, tools or docs.

## Where things stand

### Android (shipped)

- **Emulator folders on the card.** Move Emulator Files to microSD (`NanoSdMove.cpp` `emuMoveStart`, 1076) points each emulator's whole folder at `<card>/emulator_config/<emu>`: settings, saves and states together. RetroArch's folder is `persist.gammaos.retroarch.dir`, and its `retroarch.cfg` and `config/` (core options, overrides, remaps) live there (`NanoRaConfig.h` `raDirKeys`; launch config `raLaunchConfig`, mirrored by the framework's `NanoRetroArchConfig.java`). PPSSPP's memory stick holds `PSP/SYSTEM/*.ini`; Flycast's `emu.cfg`, DraStic's and drastic-nano's configs are in their folders too. `persist.gammaos.nano.emu_sd` says the files are on the card.
- **App-private settings mirrored.** `NanoEmuSync` keeps 18 items (Android preferences, ScummVM's `scummvm.ini`, Vita3K's `config.yml`, RetroArch autoconfig and the rest, `NanoEmuSync.cpp` `items`) in step with `<card>/emulator_config/<emu>/app/`, three ways per file with a base in `/data/system/nano_emu_sync.txt`; on a clash the card wins (`decide`). It runs at card adoption, every 10 s at the home screen and just before an emulator starts (`emuSettingsSyncLaunch`). A card new to the device with emulator files asks "Use the Card's / Keep This Device's" (`emuSdForeignDialog`).
- **So every Android device using a card shares one set today.** That is what OA-46 replaces.
- **Picks.** Per system: the launch fields of `/data/system/nano_systems.json`, and in store mode `ES-DE/nano/systems.json` on the card, whose copy wins (`esdeStoreAdoptSystems`, `NanoMenuXmb.cpp` 1123), plus ES-DE's `<alternativeEmulator>` (written by `esdeStoreSaveSystemEmus`, adopted by `esdeStoreApplySystemEmus`, `NanoMenuPS3EmuCatalog.cpp` 833-913). Per game: `/data/system/nano_game_emulators.json` outside store mode; in store mode `<altemulator>` or `ES-DE/nano/emulators.json` (`setGameEmulator`, 708; `esdeStoreSaveGameEmu`, `NanoEsdeStore.cpp` 1522).
- **Theme.** Local properties only (`persist.gammaos.nano.ndstheme`, `.esde.*`, `.ps3xmb.*` and the rest), read at start (`NanoMenu.cpp` 1535-1600) and by the theme engine (`NanoThemeEngine.cpp` 504-508). The ES-DE rows write through `esdeMenuApplyOption` (`NanoMenuEsdeMenu.cpp` 246); the XMB rows through the binding table (`NanoMenuPS3Menu.cpp` 9869 and the write at 12657-12667) and `applyThemeSetting` (12169). Defaults come from `mods/nano-theme.props` (OA-1, OA-35). Downloaded themes go to `/data/system/nano_esde_themes` (gap G14).
- **Thimsy settings read from the card.** In store mode, 12 scraper preferences (`persist.gammaos.scraper.*`, `kEsdeSettingProps`, `NanoEsdeStore.cpp` 1703-1723) are copied from the card's `es_settings.xml` into local properties (`esdeStoreApplySettings`, 1733-1757) and written back on a change (`esdeStoreSettingChanged`, 1771, called from `NanoMenuPS3Menu.cpp` 12667). `systems.json`'s shared fields are adopted from the card too (`esdeStoreAdoptSystems`). §2.6 decides both.

### Linux

- **Live config is on the system card's ext4** (`/storage/.config/retroarch/retroarch.cfg`, `Launcher.h` 81). RetroArch gets the card's shared folders through a per-launch append config (OA-21, `LIBRARY-FORMAT.md` 4.17). The PPSSPP and ScummVM merge layers (W7-INTEROP-11, -12) are designed, not built.
- **Wave 8 (`step/w8-emu`, merged into `linux-next`, uncompiled)** built OA-38: `nanoplat::Emulators` (`coreInstalled`, `appInstalled`, `imageDefaults`, 4c800fc); the image's defaults seeded once into `nano_emu_defaults.json` (ebc12c7); a launch whose pick cannot run starts with the image default, then the system's own emulator, then a custom system's first catalog emulator, for that launch only and never recorded (7712435, 9db53ae, 4aad6c0); a label for an emulator that cannot run kept as the pick (`esdeStoreLoadGameEmus`); the systems heal skipped in store mode (W8-EMU-20); `systems.linux.json` retired; `LIBRARY-FORMAT.md` rewritten for shared picks (f933326, 350fcb8, f303d13).
- **Single-card devices:** `/storage` is on the same physical card as the games partition, so the local set and Thimsy's local settings move with the card when it moves to another unit. §1 and §5.4 deal with that.

## 1. Device identity

**The id is the platform plus a hash of the unit's chip serial**, written `<platform>-<16 hex digits>`, lower case: `android-3f9a0c1e5b7d2a64`, `linux-9c1d0e7a42b35f86`.

- **Hash:** FNV-1a 64 of `thimsy-unit:` followed by the serial as read, printed as 16 lower-case hex digits. It is the hash Nano already uses for card files (`esdeTextHash`), so no new library. It keeps the raw serial off the card. It is not a secrecy guarantee: serials are short.
- **Platform:** `android` or `linux`. A dual-boot ARC-D therefore has two sets on one card, as OA-46 decided. The two sides' serial strings may differ (different loaders write them); nothing depends on them matching.
- **Label:** `device.json` beside the set (§2.2) holds the model's descriptor id and display name (`multi_device_plan.md` decision 19, the same on both builds), where the id came from, and dates. The user's own device name is not written (it stays on the device).

**How each platform reads the serial** (behind `nanoplat::DeviceIdentity::unitSerial()`, first good answer wins):

| Platform | Order | Notes |
|---|---|---|
| Android | `ro.serialno` (`ro.boot.serialno`, from the loader's `androidboot.serialno`); then `/sys/devices/soc0/serial_number` (Qualcomm); then a `Serial` line in `/proc/cpuinfo`; then the eMMC CID (`/sys/block/mmcblk0/device/cid`) | Unisoc loaders take the serial from the factory data; Rockchip's take vendor storage, else derive one from the chip id **(verify on the Cube and the ARC-D)**. The CID is the storage chip's, unique per unit, used only when no SoC serial is usable. |
| Linux, RK3566 and other Rockchip | the chip id from nvmem, read by thimsy-session as root and published as `/run/thimsy/unit-serial` (`rockchip-otp0` on RK3566/RK3568, `rockchip-efuse0` on RK3326, offsets per SoC **(verify)**); then `/proc/device-tree/serial-number` (U-Boot's `serial#`, NUL-terminated); then a `Serial` line in `/proc/cpuinfo` | The chip id comes first because it cannot move. U-Boot sets `serial#` only when the variable is empty, so if its environment is ever saved to the system card (env in MMC), `serial#` would follow the card to another unit **(verify per device where U-Boot keeps its environment)**. arm64 mainline kernels print no `Serial` line, so the last step only helps 32-bit kernels. |
| Linux, later families | that family's nvmem through thimsy-session first; then the device-tree node (Allwinner U-Boot sets `serial#` from the SID **(verify)**) | added with each family |

**A serial is refused** when it is empty, shorter than 6 characters, `unknown`, all one repeated character, or on a short list of factory placeholders (`0123456789ABCDEF`, `0000000000000000`, `1234567890`). The list is data, with a test.

**Waiting for the serial (Linux).** thimsy-session always writes `/run/thimsy/unit-serial`, empty when it found no chip id, so the file's presence means the answer is in. Nano waits for it (up to 15 s *(guess)* after start). Until then the id is pending: no set is synced, nothing is written to the card, and launches use the live files as they are. A random id is made only when every source of the platform has answered and none is usable, never because a source is not ready yet.

**Two units with the same serial.** A model whose units share one serial (a factory string, or a vendor-storage value cloned across units) would give one id to two units. To catch it, `device.json` records `fp`: FNV-1a 64 of a second hardware value from a different source than the serial: on Android the eMMC CID, or the Wi-Fi MAC when the CID was the serial; on Linux the Wi-Fi MAC, or the nvmem chip id when the serial came from elsewhere. Never anything stored on the system card **(verify on the Cube and the ARC-D which values each exposes, and that the MAC read is the factory one, not a randomised one)**. When the card holds a set for this id whose `fp` differs from this unit's, the two units collide: this unit takes the id `<platform>-` plus the hash of the serial and the fingerprint together, with `"source": "serial+fp"`, and offers §4.5's copy. The choice is kept in a local list, fingerprint hash to id (§3), so the id stays the same with the card out. With no readable fingerprint there is no check; Settings > About shows the id, so a clash can still be seen.

**With no usable serial**, the id is `<platform>-` plus 16 random hex digits, made once and kept locally (Android `/data/system/nano_device_id`, Linux `/storage/.config/thimsy/device-id`), with `"source": "random"` in `device.json`. Limits: a wiped Android device gets a new id (its old set stays on the card; §4.5 lets the user copy it); a Linux card with a random id that moves to another unit with no serial carries the id with it.

**The serial wins every start.** The id is recomputed from the serial at each start and the cached file is used only when no serial is readable. Reason: on single-card Linux, `/storage` moves with the card, so a cached id would follow the card to another unit and that unit would use the first unit's set. The fingerprint list is the only exception, and it is keyed by the fingerprint, so it never applies on another unit.

The per-platform folders the contract drafted for Linux (`retroarch/linux/saves/`, `retroarch/linux/states/`, `<emu>/linux/`) are withdrawn under OA-53; no Linux card has shipped, so no card has them.

### 2.2 A set

`device.json` (schema `linux/schema/emu-set.schema.json`, new, strict; not `device.schema.json`, which is the hardware `device.json` of `docs/linux/IMPLEMENTATION.md` E.7):

```json
{ "version": 1, "id": "linux-9c1d0e7a42b35f86", "platform": "linux",
  "model": "anbernic-rg-arc-d", "name": "Anbernic RG ARC-D", "source": "serial",
  "fp": "5e0a9c41d2b7f318", "thimsy": "0.2", "first": "2026-12-01", "last": "2026-12-03" }
```

The local set's `device.json` has the same form. Its `id` names the set whose files are live (§5.4), and it adds `changed` (false until a file of the set is first changed after install, §4.2) and `migration` (§6.1).

`picks.json` (schema `linux/schema/picks.schema.json`, new, strict at the top, open per entry):

```json
{ "version": 1,
  "systems": { "psx": { "launchType": "libretro-core", "coreSo": "pcsx_rearmed_libretro_android.so",
                        "key": "core:pcsx_rearmed" } },
  "games":   { "n64/Mario Kart 64 (USA).z64": { "label": "Mupen64Plus-Next", "am": "",
                                                  "key": "core:mupen64plus_next" } } }
```

- `systems` is keyed by `systems.json`'s `id`; the fields are the launch fields' own names (`launchType`, `coreSo`, `package`, `launchArgs`, `intentTemplate`), which both builds use (`NanoPlatform.h`'s `Emulators` names emulators the Android way on every platform). `games` is keyed by the game key, form (c) of `LIBRARY-FORMAT.md` 2.2, with `emulators.json`'s fields. `key` is the portable key, informative only.
- **Local game picks use the same key plus the card id:** `<card id>/<system>/<rel>`, with the card id the sync base uses (§5.2), for a game under a card's `ROMs/`. The launch path converts the path apps open (`gameEmuKey`, `NanoMenuPS3EmuCatalog.cpp` 651-655) by stripping `/storage/<vol>/ROMs/`. Only entries whose card id is the set's card go to and from `picks.json`, with the card id stripped or added; so a card with a new volume id, or a second card (OA-25), neither duplicates nor drops an entry. Games elsewhere (internal storage, outside `ROMs/`) keep their path and stay local.
- **A system pick** is a system whose launch fields in `nano_systems.json` differ from its entry in `nano_emu_defaults.json` (W8). Only those are written to `picks.json`; a system with no entry uses the image default (§5.7).
- **Settings files per emulator** come from the emulator's definition (§2.8): its `files.settings` entries, one per file or folder, each with its base folder on each platform and its flags (`many`: not checked just before a launch; `skip`: subfolders left out). Nano holds no list of its own. §2.7 gives the first cut the shipped definitions carry.

  A set never holds shared storage (§2.7) or a definition's `files.exclude` entries. Caches, logs, shader caches and any file over 16 MiB are never in a set either; that is a rule of the set code, whatever a definition says.

  SeedlessDS's `files/SeedlessDS/user` item (`NanoEmuSync.cpp` 51) syncs the whole folder except `backup` and `savestates`, so it may hold in-game saves **(verify what it holds)**. Until checked, its definition keeps the folder out of the set and today's shared mirror stays; then its settings files go under `files.settings` and its saves under `files.shared` (OA-53).

### 2.3 Picks and ES-DE's files

- **Thimsy keeps picks only in its per-device sets.** From this change on, neither build writes ES-DE's `<altemulator>` or `<alternativeEmulator>` labels or `nano/emulators.json`, and neither adopts a label change afterwards. Existing labels are read once, at migration (§6), and then left as they are.
- **What the standalone ES-DE app sees:** the labels it or a shipped Thimsy build wrote last, unchanged. Its picks are its own and do not change Thimsy's; Thimsy's picks do not reach it. Its files stay valid, since nothing removes or rewrites a label.
- **`nano/systems.json`** stays the shared system list (folders, names, order, extensions, scan sources). Its launch fields are per device (OA-46 names them): a device's own are in its set's `picks.json` and its local `nano_systems.json`. A writer keeps each existing system's launch fields on the card exactly as it read them, and writes this device's own only for a system it adds (the format requires launch fields, and shipped builds launch from them). Reading it, Nano takes the shared fields and keeps this device's launch fields (§5.7). The card's launch fields then serve only shipped builds, a custom system's first launch on a device with nothing else (§5.7) and the one-time copy of saves shipped builds left beside the ROMs (§2.7). Which fields are shared: §2.6.

### 2.4 The theme on the card (OA-51)

**Where:** both a Thimsy file and ES-DE's own keys.

- **`<theme card>/Thimsy/theme.json` is the truth.** It holds every theme key below, by the portable names `prefs.json`'s `ini` column already gives them, with values in the device store's own encoding (so no conversion):

  ```json
  { "version": 1,
    "theme": { "home.theme": "3", "esde_theme.set": "colorful-simplified-es-de",
               "esde_theme.color_scheme": "colorful-dark", "esde.settings_theme": "minima" } }
  ```

  Schema `linux/schema/theme.schema.json` (new). Unknown keys are kept. JSON, not INI: `settings.ini` and its dialect are dropped (OA-47), and Nano already reads and writes JSON (`NanoJson`) on both builds.
- **ES-DE's `es_settings.xml` gets four keys mirrored**, so the standalone ES-DE app shows the same theme: the set, `ThemeVariant`, `ThemeColorScheme`, `ThemeFontSize`. They go into the `es_settings.xml` of the store Nano uses, only when the chosen set exists in that store's `themes` (the rule `LIBRARY-FORMAT.md` 1.4 already has). This is a display copy for the ES-DE app under OA-51, not OA-32 Q4's portability write: `theme.json` is the truth. The bundled ES-DE app keeps its settings in `/sdcard/ES-DE` (`mods/37-esde.sh`), so the mirror reaches it only when that is the store **(verify which `es_settings.xml` the bundled ES-DE app reads)**. ES-DE 3.x names the set key `Theme`, older versions `ThemeSet`: the writer updates whichever the file has, and when it has neither, uses the name of the app version Thimsy bundles (`mods/37-esde.sh`, `VERSION="3.5.0"`) **(verify which name 3.5.0 writes)**. `ThemeAspectRatio` is never written (W7-INTEROP-9 stays). The other ES-DE keys Nano has counterparts for (`MenuColorScheme`, `MenuBlurBackground`, `ThemeTransitions`) are not mirrored in v1: their values differ from Nano's **(verify)**.
- **A theme edit made in the ES-DE app** is taken into `theme.json` at the next sweep only when all of these hold: `es_settings.xml` is newer than Nano's last mirror write; the ES-DE app is not running; one of the four keys differs from what Nano mirrored last and is not the value it mirrored before that; and the set exists on the card. Reason: ES-DE rewrites the whole file from memory whenever any of its settings is saved, so an app that read an older theme at start writes that theme back; without these checks Nano would take it and revert the theme on every device (owner question 4).
- **The theme keys (31).** The rule: a key that chooses which interface Nano shows, or how it looks, and does not depend on the screen or the buttons.

  | Look | `home.font`, `home.wallpaper_effect`, `home.wallpaper_dim` | `font`, `wallpaper`, `wp.scrim` |
  | XMB style | `xmb.theme`, `xmb.color`, `xmb.color_custom`, `xmb.background`, `xmb.font`, `xmb.day_night`, `xmb.wave`, `xmb.wave_explicit` | `ps3xmb.theme`, `.color`, `.color_custom`, `.bg`, `.font`, `.daynight`, `.wave`, `.wave_explicit` |
  | DSi style | `dsi.dark`, `dsi.effect`, `dsi.tile_icon`, `dsi.rom_title` | `nds.dark`, `nds.effect`, `nds.tileicon`, `nds.romtitle` |

### 2.7 Shared storage and settings, per emulator (OA-52, OA-53)

Every file an emulator keeps is one of three kinds, and its definition says which (§2.8):

| Kind | Examples | Where | Rule |
|---|---|---|---|
| Per-device settings | graphics, controls, performance, folders, per-game settings | the live file, the local set, the card set (§2.2) | OA-46 |
| Shared storage | emulated drives (installed games, updates, DLC, firmware, system save areas), in-game saves, save states, memory cards, BIOS and keys | the emulator's card folder `emulator_config/<card folder>/`, `bios/`, `retroarch/system/` | one copy on the card for every device; never in a set; no device mirror (OA-52, OA-53) |
| Left out | caches, shader caches, logs, crash dumps, temporary files | the emulator's local folders | never synced, never on the card |

**No mirror.** The local set holds settings only. With the card out, an emulator whose shared storage is on the card does not start ("<emulator> needs the card"), as shipped Android builds do today (`README.md` 586-587). usb_storage_plan.md's fallback to internal storage then covers settings only: a fallback copy of a drive or a save folder would be the mirror OA-52 and OA-53 rule out, and two copies would split a save (owner question 20). On single-card Linux the card is always in.

**Android with the emulator files on internal storage** (`emu_sd` off): recommended, they stay there until the user runs Move Emulator Files, as today. Nothing is mirrored either way (owner question 19). The rule that makes this hold: a shared entry's `card` path is under the emulator's *shared root*. On Linux, and on Android with `emu_sd` on, that is `<card>/emulator_config/<card folder>/`. On Android with `emu_sd` off it is the emulator's internal root, `files.roots.android.internal` (`user_emulators_plan.md` §1a): the folder Move Emulator Files moves into the card folder, for RetroArch `/storage/emulated/0/RetroArch` (`kRaDefSd`), for ScummVM `/data/data/org.scummvm.scummvm/files`, whose `saves/` is `kScummvmDefSaves`. So:

- `config_key` and `append` values, and `{card}` in `point.rest`, name the internal root; RetroArch's family folders are `/storage/emulated/0/RetroArch/saves/<family>/<system>/`, and ScummVM's `savepath` stays `kScummvmDefSaves`, so its saves are found.
- A `config_key` whose live value names another folder (one the user chose) is left as it is while `emu_sd` is off; Move Emulator Files moves from that folder, as today (`NanoSdMove.cpp` 1231-1242).
- A `link` entry makes no link: the local folder is the one copy.
- No card is needed to start, and nothing waits for one.
- Shared storage reaches the card only through Move Emulator Files. It moves the whole root, so the paths under it do not change, and the next launch points at the card.

**How an emulator is pointed at the shared storage.** The definition names a method for each shared entry (`point`, §2.8). The code implements the methods, never a per-emulator case:

| Method | Platforms | What it does | Shipped use |
|---|---|---|---|
| `slot` | Android | the emulator's whole folder is on the card, so its storage is already there; its settings files in that folder are a live slot, filled from this device's set before each launch (§5.6) | RetroArch, PPSSPP's memory stick, Azahar's SAF folder, Flycast, DraStic: the folders Move Emulator Files already puts on the card |
| `link` | both | the folder stays local, and each shared subfolder becomes a link to the card folder. Android: today's Dolphin and hakuX link lists (`NanoSdMove.cpp`; apps reach `Android/data` directly, `README.md` 575-579). Linux: a symbolic link on `/storage` (ext4) to the card's folder, which the exFAT card itself could not hold | Dolphin's `Wii/`, `GC/`, `StateSaves/` on Android; PPSSPP's shared subfolders on Linux |
| `config_key` | both | a key in a per-device settings file names the card folder. Nano writes it into the live file before each launch from where the shared root is now (§5.6 step 3). A key whose `card` path has no launch placeholder keeps that path between launches: its `point.rest` is `{card}/<card path>` (the internal root while `emu_sd` is off), as RetroArch's `savefile_directory` rests at `{card}/saves`. So the emulator opened outside Nano (Vita3K, Eden or Azahar from the app drawer, to install firmware, games, updates or DLC in their own UI; ScummVM's own launcher) works on the same one copy, as it does after Move Emulator Files today. The stored path names the card even while it is out; opened outside Nano then, the emulator finds the folder missing. A value for one launch only (a `card` path with a launch placeholder, every `point.set` key) goes into the definition's per-launch copy instead (`files.launch_copy`, §5.6), never into a file another launcher reads | Vita3K's `pref-path` in `config.yml` **(verify)**; Eden's and Azahar's `[Data%20Storage]` `nand_directory` and `sdmc_directory` **(verify on the Android builds)**; Dolphin's `NANDRootPath`, `MemcardAPath`, `MemcardBPath` **(verify)**; a PS2 emulator's `[Folders]` keys **(verify)**; ScummVM's `savepath` |
| `append` | Linux | a per-launch append config written to `/run/thimsy/`; each of its keys in the live `--config` file is recorded before the run (its value, or that it is absent) and put back after it (§5.6 step 4) | RetroArch's `system_directory`, `savefile_directory`, `savestate_directory`, `cheat_database_path` (`LIBRARY-FORMAT.md` 4.17) |
| `bind` | Linux | thimsy-session bind-mounts the card folder over the local one for the run, through the OA-30 request path | only an emulator that refuses a link **(verify per emulator)**; definitions of origin `system` or `index` only |

Where a definition could use more than one, the recommended order is `config_key`, then `link`, then `bind` (owner question 23). `LIBRARY-FORMAT.md` 4.18's bind mounts for PPSSPP become links unless PPSSPP refuses them **(verify)**.

**A real folder where a link belongs** (the emulator ran once before Nano made the link, an app update made the folder again, the link was lost): before the link is made, the folder is merged into the card folder, on both platforms. A file the card lacks is copied there; an identical file is skipped; when both exist and differ, the newer takes the card path and the other is kept as `emulator_config/conflicts/<id>/<card folder>/<rel>`, outside every folder an emulator reads, and Settings says so once. Only when every file is on the card (size and hash checked) is the local folder removed and the link, made under a temporary name, renamed into its place. A merge cut short leaves the local folder as it is and runs again at the next launch. With the card out nothing is merged. Nothing is dropped.

**Saves and states per core (OA-53).** One copy for every device and both platforms; differing cores never share a file. Where a save lives is fixed by the core that writes it, never by a pick or by the card's launch fields, so no later change can move or hide one:

- **RetroArch in-game saves: one fixed folder per save family and system.** Every launch by a new build, on both platforms, puts the game's in-game saves in `retroarch/saves/<family>/<system>/[<subdir>/]` under the shared root (above), never beside the ROM. `<family>` is the launch entry's `save_family` (`user_emulators_plan.md` §1a), or its `core` when it has none; `<system>` is the game's system folder under `ROMs/`, and below it `<subdir>` is the path of the game's own folder, empty for a game directly in `ROMs/<system>/`: `ROMs/snes/USA/Game.sfc` saves in `saves/<family>/snes/USA/`, `ROMs/snes/Europe/Game.sfc` in `saves/<family>/snes/Europe/`, `ROMs/snes/Game.sfc` in `saves/<family>/snes/`. RetroArch names a save after the ROM's file name, so without that level two games of one name in two subfolders of one system would write one file. The folder depends only on the entry being launched and the game. So nothing that happens later to `systems.json`'s launch fields (a shipped build re-picking, a store created after saves exist) or to a pick can move or hide a save. Two cores write one file only when their definitions name one family, which is OA-21's `saveCompatible` rule carried as data (the family table, `LIBRARY-FORMAT.md` section 5). A core of one name on both platforms is one family, so its Android buildbot build and its Linux source build write one file: OA-21's round trip (the Mesen case, §8.5's verify list) checks each such core's in-game save before Linux's first release, and a core that fails it gets its own `save_family` in its Linux launch entry (for example `mesen.linux`, *name form proposed*), so the two builds never write one file (owner question 27). The `<system>` level keeps apart two systems' games of one name under a multi-system core (Genesis Plus GX). A game moved to another subfolder no longer finds its save: the old folder's save of its name and family is listed in Older saves for it, with the launch's one-line notice when the new folder has none, and is never taken in on its own, since it may be another game's of the same name.
- **Files and folders a core keeps itself** (`opera/per_game/`, `yabasanshiro/backup.bin`, `mame/`, `fbneo/`) land below the same folder, the game's, because RetroArch hands the core the save folder. So a core that keeps one file for every game (Sega CD's `scd_U.brm`) keeps one per subfolder, and a subfolder named like a core's own folder (`ROMs/arcade/mame/`) shares that folder with it, their files differing by name (owner question 28). MAME's `cfg/` (its own per-game input, DIP switch and counter settings) stays with the rest of `mame/`, shared: a path cannot be both a setting and shared storage, and the libretro MAME cores have no option that moves `cfg/` alone **(verify for `mamearcade` and `mame2003_plus`)**. Pad controls stay per device in RetroArch's remaps, which are in the set. Owner question 24.
- **RetroArch save states.** Always `retroarch/states/<core>/<system>/[<subdir>/]`, `<core>` being the launch entry's `core` and `<subdir>` as for saves, on both platforms. RetroArch reads states only from that folder, so a state is offered only to its core. A core named differently on the two platforms is kept apart, which is safe. A core of one name on both platforms shares one folder at once (OA-53), so an Android buildbot build and a Linux source build of it must read each other's states: each such core is checked by `linux_handheld_plan.md` question 11's round trip (§8.5's verify list) before Linux's first release. A core that fails it gets a distinct state folder per platform build in its definition: its Linux launch entry sets `state_core` (for example `pcsx_rearmed.linux`, *name form proposed*), which fills `{core}` in the states path in place of `core`, so neither build is offered the other's state or overwrites its `.state.auto` (recommended). Or the folder stays shared, each state gets a stamp (core library name, version, platform), and a launch whose stamp differs runs with `savestate_auto_load` `"false"` in `point.set` **(verify)**, the state still listed for a manual load with a warning. Owner question 27.
- **Saves and states made outside these folders** (*legacy files*). Shipped builds write every save and state beside the ROM; a contentless core, or a user who turned "save in content dir" off, left them loose in `retroarch/saves/` and `retroarch/states/`, in RetroArch's own per-core folders there (`saves/<core name>/`), or, with RetroArch's sort by content directory on, in `saves/<content dir>/` or `saves/<core name>/<content dir>/` (`<content dir>` being the name of the ROM's own folder **(verify)**); RetroArch started outside Nano keeps writing beside the ROM, because Nano's launch values go only into its per-launch copy (§5.6) and the slot keeps the shipped build's values, or the user's. RetroArch's definition lists each of these places in the entry's `legacy` (below). New builds take them in by copy, never by a move, at a launch of the game, in three steps:
  1. **Whose file it is.** A file in a per-core folder (`<core name>/`, `<core name>/<content dir>/`) belongs to the family (for a state, the core) of the launch entry whose `core_name`, RetroArch's folder name for the core (the core's `library_name` **(verify per core)**), names the folder. A file beside the ROM, loose in the folder's root or in a content-directory folder belongs to the game's *legacy family*: that of the game's legacy pick, else of the system's. A legacy pick is what a shipped build launched. On a card with a store: the game's `<altemulator>`, else its `emulators.json` item, and for the system the card's `systems.json` launch fields; new builds never write any of these, and read them here only to know whose a file is, never as a pick. On a card with no store: the picks this device's shipped build had, kept unchanged in `<local set>/legacy-picks.json` (§6.1 step 3). With neither, the owner is unknown.
  2. **Taken in on its own** only when the file belongs to the launching entry's family (for a state, its core) and the folder has no save (state) for the game. With several such files the newest is taken. A place whose path does not name the game's system and folder (loose in `saves/` or `states/`, a per-core or content-directory folder) can hold the file of a game of the same name in another system or subfolder: such a file is taken in on its own only when no other game on the card has that name, else it is listed for each of them. The copy is recorded in the folder's `.thimsy-legacy.json` (the source path relative to the card, its size, time and hash). The source stays where it is.
  3. **Never hidden.** Every other legacy file for the game (another or an unknown family, a folder that already has a save, a source that changed after it was taken in because a shipped build or RetroArch outside Nano played the game again) is listed in Game Options > **Older saves** with its place, date and owner, and the user can copy one in. The folder's current file is first kept beside it with `.<date>.bak` added to its name, or `.<date>.2.bak`, `.<date>.3.bak` and so on when that name is taken, so no `.bak` is ever overwritten; RetroArch never reads them, and no `names` pattern matches a name ending in `.bak`. Older saves also lists every `.bak` beside the game's save or state and every `thimsy-older/` file of its name (rule 2 below), so each can be copied back. A state is listed only for the core it belongs to, or with a warning when its owner is unknown: another core cannot load it (OA-53). A file of the launching family that is newer than the folder's save, or a swept file of the game's name in `thimsy-older/` that is newer than it (or the folder has none), also gives a one-line notice at the launch. Nano never copies another family's file by itself, so two cores never write one file.

  So a later change of the card's labels or launch fields can only change whose a file not yet taken in is. A save in a family folder never moves, and every legacy file is either taken in or listed. Owner questions 17 and 18.
- **Which definition fields name the folders and keys.** RetroArch's definition has `files.shared` entries of class `saves` and `states` (one per platform) whose `card` paths use placeholders, `saves/{save_family}/{system}/{subdir}` and `states/{core}/{system}/{subdir}` (`user_emulators_plan.md` §1a defines `{game}`, `{system}`, `{subdir}` and `{rom_dir}`), and whose `point` names the key: on Android `config_key` in `retroarch.cfg` (`savefile_directory`, `savestate_directory`), on Linux `append` with the same keys. `point.set` lists the keys fixed for the launch (`sort_savefiles_enable`, `sort_savefiles_by_content_enable`, `sort_savestates_enable`, `savefiles_in_content_dir`, `savestates_in_content_dir`, all `false`). On Android the `config_key` and `point.set` values go only into the per-launch copy that the definition's `files.launch_copy` names (§5.6), and Nano never resets these keys in a stored file (the slot, the local copy, the card set): each keeps the value the user, a shipped build or RetroArch left there. A shipped build's file (`nano/test/fixtures/retroarch/retroarch_shipped.cfg`) has `savefiles_in_content_dir` and `savestates_in_content_dir` `true`, so a shipped build or the ES-DE app using the slot, during a Nano run or after it, saves beside the ROM, as it always has, and finds its own saves; and a user who turned Explore or History off in RetroArch keeps that outside Nano. So these entries carry no `point.rest`: it is only for a file with no launch copy. On Linux the append config sets the keys for the run, but RetroArch's `config_save_on_exit` may write them into the `--config` file at exit **(verify against the RetroArch version the lock pins)**. So step 3 records each `append` key's value in the live file, or that it is absent, and step 4 puts that back before the file is copied or hashed: the value is restored, and the key is removed only when it was absent. A value the user had there (`system_directory`, `cheat_database_path`, a menu key) survives the run, and Linux's entries need no `rest` either. `legacy` lists the places of step 1; a path without `{rom_dir}` is under the shared root.   The rule is generic: any launch entry with `core` (and `save_family`, `core_name`) and any shared entry whose `card` path has a placeholder get the same handling, so a user's definition for another libretro frontend gets it too. Nano's code names no core and no key. This replaces Linux's `retroarch/linux/saves/<system>/` and `.../states/<system>/`, and settles `LIBRARY-FORMAT.md` §10's "which Android core decides a shared save": none does.
- **No other core or game during a Nano launch.** The save and state folders are fixed for the whole run. A core or game loaded from RetroArch's own menu (Load Core, Load Content, History, Favorites, the `.lpl` playlists) would write into them: the same game under another family's core would overwrite the family's save, another core's state would be offered to the launched core, and another game's save would land where no launch of that game reads it. Two rules stop this:
  1. **The loading menus are hidden for the run.** The saves entry's `point.set` also holds `menu_show_load_core`, `menu_show_load_content`, `menu_show_load_disc`, `menu_content_show_history`, `menu_content_show_favorites`, `menu_content_show_playlists` and `menu_content_show_explore`, all `"false"`, plus `menu_content_show_contentless_cores` `"0"` and `menu_content_show_netplay` `"false"` **(verify these two)**. On Linux they go in the append config. The names are RetroArch's `retroarch.cfg` keys as known **(verify each against the RetroArch version the lock pins)**. Like the save keys, they go only into the per-launch copy, and no stored file is reset: each keeps the user's own value, so a shipped build or the ES-DE app, which read the stored files, shows its menus as the user left them. Kiosk mode (`kiosk_mode_enable`) is not used: it also hides RetroArch's settings, which a Nano launch keeps. Owner question 26.
  2. **The after-run sweep** (§5.6 step 4) catches what the menus miss (a route not hidden, a RetroArch version with other key names). A file written during the run directly into the launch's save or state folder (never one in a subfolder below it: those belong to other subfolders' games or to a core's own folders) whose name is not the launched game's is moved to `<shared root>/thimsy-older/<its path under the shared root>`, which no emulator reads, never over a file already there (a taken name gets `.2`, `.3` and so on added), and listed in Older saves for each game of that name on the card, owner unknown. It is never left in place. Only names that match the entry's `names` patterns (`{game}.srm`, `{game}.rtc`; for states `{game}.state*`) with another game's name are swept, so the files and folders a core keeps itself (`scd_U.brm`, `mame/`) stay.

  Neither rule catches the launched game run under another core through a route the menus miss, since its file has the game's name. The hidden menus are the guard for that case.
- **Standalone emulators** keep saves and states in their own shared folders (PPSSPP's `SAVEDATA` and `PPSSPP_STATE`, Dolphin's `GC/` and `StateSaves/`). No other emulator writes there, so they stay apart by folder. The same emulator on both platforms (PPSSPP) shares one folder; `card.json`'s `emulators` versions (`LIBRARY-FORMAT.md` 4.16) warn when the other side's build was newer. `ppsspp/linux/PSP/PPSSPP_STATE/` is withdrawn.
- **BIOS** is one copy: `bios/` (the drop folder), `retroarch/system/` and each emulator's BIOS folder named by its definition's `bios` block (`user_emulators_plan.md` §6). The BIOS installer writes there; its installed-file records stay on each device (`LIBRARY-FORMAT.md` 4.14). Key files (Eden's `keys/`, Azahar's `sysdata/`) count as BIOS.

**Sizes.** Shared storage is the bulk of `emulator_config/`, and these rules keep one copy of it, on the card:

- An emulated drive can be large *(guesses)*: Vita3K's `ux0` holds installed Vita games of 1 to 4 GB each; Eden's NAND and SD hold firmware (a few hundred MB) plus installed updates and DLC (GBs); Azahar's `sdmc` holds installed titles (hundreds of MB to GBs); hakuX's disk image is GBs; Dolphin's Wii NAND is up to 512 MB. PPSSPP's `SAVEDATA` and PS2 memory cards (8 MB each) are small.
- No mirror means no second copy: Android's internal storage and Linux's 256 MiB `/storage` (`linux/board/rk3566/genimage.cfg`) never hold a drive. The sets stay small: settings only, each file capped at 16 MiB.
- More devices cost nothing: one copy serves them all. Per-core folders cost a little: a game played with two cores has two saves and two state folders.
- The card needs the room. An install inside an emulator that fills the card fails in that emulator. Move Emulator Files and the migration check free space before they copy, as today.
- A FAT32 card cannot hold a file over 4 GiB (a disk image, a large installed title). `LIBRARY-FORMAT.md` 3 already recommends exFAT; Nano warns when a definition's `drive` entry is on a FAT32 card *(proposed)*.

## 4. The "SD card settings" switch (emulator sets)

### 4.1 Key and states

`persist.gammaos.nano.emu_card_sets`, class D (local). Its `prefs.json` row is added with the code that reads it: `test_prefs.py` fails on a key `nano/` does not use yet. Values: unset, `1`, `0`.

| State | Meaning |
|---|---|
| Off (`0`) | Only the local set is used. The card set, if any, is neither read nor written. |
| On, in use | The card set exists and is synced with the local set; the card wins. |
| On, waiting | On, but no card, a read-only card, or a card set Nano cannot read: the local set is used and the card is retried at each sweep. Settings shows why. |

OA-46's lookup says: "Thimsy uses the card's set that matches this device; when there is none, it uses the device's local set." The plan reads it with the Mirror rule, which gives the card priority "when the switch is on": with the switch off, a card set for this id is ignored, not used read-only. Reason: a read-only card set would take edits that are never written back, so each edit would vanish at the next start while the card is in. Owner question 16.

The row: Settings > Game Settings > **SD Card Settings**, with a status line ("Using this card's settings for this device", "No card", "Card is read-only", "Card settings unreadable: using this device's").

### 4.2 Turning it on

1. The card has **no set for this id**: the local set is copied to the card: each settings file, then `picks.json`, then `device.json` last. A copy that stops part-way has no `device.json`; it is a partial set and the copy resumes at the next sweep (§5.5).
2. The card **already has a set for this id** (made before the switch was last turned off, or before a reinstall): Nano asks "This card has emulator settings for this device from <date>." with "Use the card's" and "Use this device's". The first choice is "Use the card's" when the local set is unchanged since install (local `device.json` `changed` is false: a reinstall or a wipe, the usual reason the card already has this id's set), else "Use this device's". The replaced copy is kept once: a card set in `devices/<id>/.previous/`, a local set in `<local set>/previous/`, each overwriting the copy kept before. Owner question 6.
3. The switch is then on, in use.

### 4.3 Turning it off

The sync stops. The card set stays on the card as it is (a stale copy). Nothing is deleted on either side. Turning it on again is §4.2 case 2.

### 4.4 Already on, card has no set for this device

A card new to this device (from another device, a fresh card, a card from before this change): the local set is copied to the card as in §4.2 case 1, with no question. Other devices' sets are never read or changed.

### 4.5 Copying another device's set

Settings > Game Settings > **Copy settings from another device** lists the card's sets of the same platform by their label (model, last used). Choosing one replaces this device's local set (and card set, if the switch is on) after a confirm. Before the replace, the local set is kept in `<local set>/previous/` and the card set in `devices/<id>/.previous/`, so the copy can be undone. The list also shows the slot files kept from shipped builds (`slot-kept/legacy/`, §5.6) as "Old shared settings". Never automatic. It covers a new unit of the same model, and a device whose id changed (a random id after a wipe). Owner question 7.

### 4.6 First-boot defaults

- **Linux:** on.
- **Android, new install:** on when setup's "Keep emulator files on the microSD card" is chosen (today it sets `emu_sd`), else off.
- **Android, update from a shipped build:** on when `emu_sd` is `1`, else off (§6).

### 4.7 The theme needs no switch

OA-51's theme always applies when a theme card is present (recommended; owner question 2). With the store on internal storage, the theme card is the slot card; with no card in, the local value is used, wherever the store is. There is nothing per device to protect, and a switch would bring back the "Use this card's settings?" question OA-32 had.

How the local value and the card's relate (recommended, owner question 1): **they are separate values.**

- Card in: the card's `theme.json` is shown. Before its values go into the live theme keys, the device's own values are saved to the local theme file (§3), once. Theme edits go to the live keys and to `theme.json`; the device's own values are not touched.
- Card out: the device's own values are put back from the local theme file, and the file is removed.
- No `theme.json` on the card yet: it is written from the device's current values (the card is seeded, as with emulator sets in §4.4).
- A key missing from `theme.json` (an older writer, a PC edit) uses the device's own value; it is written to the card the next time the theme changes.
- At start, a leftover local theme file with no card present is applied back first, so a power cut while a card's theme was shown leaves nothing behind.
- **One writer.** The home and the overlay are two Nano processes, so both take `DeviceStore::themeLock()` (a file lock, like `nano_emu_sd.lock`) around apply, restore and every `theme.json` write; only the home process applies and restores, and the overlay writes edits under the lock. The local theme file is written atomically and `fsync`ed (§5.5) before the first live key is overwritten, and removed only after every key is put back.

The live keys stay the ones every reader uses today (both Nano processes read them), so no reader changes. When the `Prefs` facade (OA-4 step 8) lands, this becomes a card layer in it instead.

## 5. Sync rules

### 5.1 Card wins

- **Emulator sets (switch on):** three ways per file, as `emusync::decide` does today: changed only on the card, the card's copy goes to the device; changed only on the device, the device's goes to the card; changed on both, or never synced with this card set, the card's wins. What looks like a mass deletion on one side is taken as never synced (today's rule).
- **Picks:** per entry, not per file. The base is a copy of `picks.json` as last synced, kept in the local set (`picks.synced.json`). An entry changed only on the card goes to the local pick files; one changed only locally goes to `picks.json`; one changed on both takes the card's.
- **Theme:** always the card's while it is in (§4.7).
- The device copy that loses a clash is kept once, as `<local set>/conflicts/<emu>/<rel>`, overwriting the previous one (owner question 11).

### 5.2 Writes

- **Nano's own changes** (a pick, the hotkey provisioning in `retroarch.cfg`, BIOS paths written into an emulator's config, a theme row) go to the local copy at once and to the card at once when the switch is on and the card is in.
- **An emulator's own changes** during a game come back after it exits: the after-run sync (§5.6) for that emulator, and the sweep.
- **Sync state** stays one line per file, with the set in the key: `<card id>\x1f<set id>\x1f<emu>\x1f<rel>`, then the device side's stamp, the card side's stamp and the card copy's hash (`emusync::baseKey`, `baseSave`). The hash is what tells a FAT time change from an edit.
- **When:** at card adoption, before and after each emulator run, every 10 s at the home screen (today's `emuSdTick` timing), and before sleep and shutdown. Never into an emulator that is running (today's rule).

### 5.3 PC edits

A file edited on the card from a PC changes its hash, so it counts as a card change and wins. `picks.json` and `theme.json` edits are read at the next sweep (`esdeStoreSweep` watches both, `esdeNoteWrite` keeps Nano's own writes from counting). A `picks.json` or `theme.json` that does not parse is not used and not overwritten (`LIBRARY-FORMAT.md` 1.2); the local values are used and Settings says so. A PC edit to an Android slot file (`emulator_config/retroarch/retroarch.cfg`, the path users know) goes to the set the slot's marker names (§5.6); to change one device's settings from a PC, edit `devices/<id>/...`.

### 5.4 A card from another device, card removal, two cards

- **Another device's card:** no set for this id, so §4.4: the local set is copied there. The card's theme is shown (OA-51), and the device's own theme comes back when the card leaves.
- **Single-card Linux, the card moved to another unit:** `/storage` moves with the card, so its live files hold the last unit's settings, and the local `device.json`'s `id` says whose. At start, before any three-way pass, when that id is not this unit's:
  1. The live files and local picks are parked as that id's set (`emu-set/parked/<that id>/`). Its sync base stays as it is (keyed by set id, §5.2).
  2. If this id has a parked set, it is put back into the live files. Else, with the switch on and a set for this id on the card, that card set is taken whole, with no base and no three-way pass. Else this unit starts from a copy of the parked files as its own set.
  3. `device.json` is rewritten with this id, last; then the normal sync runs.

  So unit A's settings come back on A however long the card spent in unit B; B's never reach A's card set, and they stay parked (and in B's card set) for B's next visit. With the switch off, the units are still parked and swapped; nothing reaches the card. The same check runs on Android, where it fires only when the id changes (a random id after a wipe, a collision id, §1).
- **Card removal:** the local set is complete, so nothing is lost; launches use it. Edits made with the card out are local; at the next insertion the three-way rule sends them to the card unless the card's copy changed too (then the card wins and the device's goes to `conflicts/`).
- **Two cards (OA-25):** only the chosen card's sets and theme are used. The other card is not read or written.

### 5.5 Partial and damaged files, atomic writes

- Every file a sync writes, on the card or on the device, is written to a temporary name in the same folder, `fsync`ed, renamed over the old one, and the folder `fsync`ed (`LIBRARY-FORMAT.md` 1.2). App-private files keep `sdWriteAppFile`'s owner, mode and SELinux label.
- A set folder without `device.json` is partial: a copy that did not finish. When this device made it, the copy resumes; it is never used as the truth until `device.json` is there.
- A settings file is copied as bytes; Nano does not parse it. Files over 16 MiB and the temporary names are skipped. A missing or empty local copy is never written over a live file (§5.6).
- A card that turns read-only or fails a write: the switch goes to "On, waiting" and the local set is used.

### 5.6 Emulators that read their own storage

Before an emulator starts (`emuSettingsSyncLaunch` on Android, the launch path on Linux), an after-run step still pending from an earlier run on this device (the home's or the overlay's: both Nano processes share one pending-run file, under a lock) runs first, so its sweep never meets this launch's files. Then:

1. With the switch on and the card in, that emulator's files are synced card to local (§5.1).
2. Its live files are brought up to date from the local copy:
   - **Live file is the local copy** (Android app-private files, all Linux files): nothing more to do.
   - **Live file on the card** (Android only: an emulator whose definition says `files.live: slot`, today RetroArch's `retroarch.cfg` and `config/`, PPSSPP's `PSP/SYSTEM`, Flycast's `emu.cfg`, Azahar's `config/` and the others in an emulator's own folder on the card, since that is the only place the emulator reads them): the folder is a **live slot**. A marker `emulator_config/<emu>/.thimsy-slot` records the set id, each file's hash as last written or taken, and `restore` when the slot's earlier files are owed back (step 5). Before the fill, each slot file is checked against the marker:

     | Slot file | Marker | Before the fill |
     |---|---|---|
     | as the marker records | this set | nothing |
     | as the marker records | another set | nothing kept: that device wrote or took the file, so its own set already has it |
     | changed | this set | taken into the local set, then the card set: a change made outside the after-run step (a run cut short, the ES-DE app or the launcher, a PC edit) |
     | changed | another set | kept as `slot-kept/<that id>/<emu>/<rel>`; that device takes it as a card-side change at its next sync |
     | any | none | kept as `slot-kept/legacy/<emu>/<rel>` (a shipped build's or a hand-made file), and `restore` set |

     Then the local copy is written in. A file whose local copy is missing or empty is not filled: the slot's file is left as it is.
   - **Emulator folders on internal storage** (`emu_sd` off): they are local copies, not slots.
3. The definition's pointing (§2.7) is applied from where the shared root is now (the card, or with `emu_sd` off the internal root, §2.7): its `config_key` entries are written with their `point.set` keys, into the definition's per-launch copy where it has one (`files.launch_copy`, below), else into the live files (for RetroArch, its folder keys go into the slot, and §2.7's save, state and loading-menu keys into the copy, all from its definition), its links are checked and made (a real folder where a link belongs is merged first, §2.7), legacy files are taken in (§2.7), the names, sizes and times of the files directly in the launch's save and state folders are listed for the sweep (step 4) and kept on the device with a run id, and a run marker `<shared root>/.thimsy-run.json` naming this set, the run id and the folders is written on the card, and on Linux each `append` key's value in the live file, or its absence, is recorded with the run id, the append config written and any bind requested; then the hotkey provisioning runs, and the per-launch copy, if any, is written last: the live file as it now is, plus the launch's values. So a stored path names only the shared root as the last launch found it, no file another launcher reads holds a launch value, and the emulator always reads the one shared copy.

After it exits (the definition's `files.after`: `exit` once the emulator's process has ended, which Nano checks on Android when it is in front again, at each sweep and at start, and on Linux through `pollChild`; `foreground` when Nano is in front again on Android). RetroArch's definition uses `exit` on both platforms: it can stay alive in the background with the launch's folders in memory, so Nano coming to the front does not end its run. Any definition with a `config_key` or `append` point, or a `files.launch_copy`, must use `exit`, so no pointing key is put back while the emulator is still alive in the background and its own config save at exit cannot undo the put-back or keep a launch value (§5.2: never into an emulator that is running):

4. With a per-launch copy, the copy is compared key by key with what step 3 wrote, through the file's format: each key the emulator changed during the run (RetroArch's `config_save_on_exit` and its "Save Current Configuration" write the copy, not the slot), other than the `config_key` and `point.set` keys, is written into the live file, so a setting changed in the run is kept and no launch value reaches the slot. Without one, the `config_key` values step 3 wrote are put back to the definition's `point.rest` values; for a key whose `card` path has no launch placeholder that is the shared-root path itself (§2.7), so the key keeps naming the one copy. On Linux each `append` key is put back as step 3 recorded it, the value restored or the key removed only when it was absent (§2.7), here and at the next start after a run cut short. So a per-launch value is never taken into a set. Then live files changed during the run are copied to the local copy, then to the card set. For a slot, only when the marker names this device's set; a slot another device or a shipped build wrote last is never taken as this device's settings. Shared storage is never copied: the emulator wrote it in place. Then the sweep (§2.7): a file directly in the launch's save or state folder that step 3's listing lacks, or that changed since, and whose name matches the entry's `names` with another game's name, is moved to `thimsy-older/` (never over a file there) and listed in Older saves; then the marker is removed. A run cut short is swept at the next start from the kept listing only while the card's marker still names this set and this run id, so nothing else has used the card's folders since. When another set's marker, a newer run's or none is there (the other side of a dual-boot ARC-D after a crash, another device after a flat battery, a later launch), the listing is dropped without a sweep and the files it would have moved stay in place. On Linux a bind is released when the game's process group ends.
5. When the marker has `restore`, the slot's earlier files are put back from `slot-kept/legacy/` and the marker is removed, so a shipped build using that card finds its own settings again.

Launch values are not settings, and only the per-launch copy or the append config holds them. A file with a per-launch copy (RetroArch's `retroarch.cfg` on Android) never gets one, and Nano resets nothing in it: the copy-back skips the pointing keys, so each stored copy (the slot, the local copy, the card set) keeps the value the user left on each such key. A file with no launch copy has its `config_key` values put back to `point.rest` (for a key with no launch placeholder, the shared-root path, §2.7) before any hash is compared. On Linux the `append` keys are put back as step 3 recorded them before any hash is compared. At start, a run cut short is finished first for every emulator that is not running: each of its live files with pointing keys, a slot or a local file, gets that run's put-back (the `rest` values, Linux's recorded `append` values) and its per-launch copy's copy-back, before any hash is compared. The slot check (step 2's table, then step 5 when owed) then runs at start, at card adoption and at each sweep, for every emulator that is not running. So a run cut short by a crash, a power cut or a flat battery is taken in and put back at the next start, and no slot is overwritten without the check.

**RetroArch on Android: a per-launch copy.** Every RetroArch start reads a stored `retroarch.cfg`: a shipped build's and the launcher's read the slot, the ES-DE app's RetroArch's default `files/retroarch.cfg`. Nano never writes a launch value into either. Each Nano launch passes a per-launch copy instead: the live file as step 3 leaves it, plus §2.7's save, state and loading-menu keys, written to a path no other launcher names, `files/thimsy-launch/retroarch.cfg` in RetroArch's own folder on device storage (the definition's `files.launch_copy`, base `media`). The copy keeps the slot's folder keys unchanged, so RetroArch still finds the slot's `config/` (core options, overrides, remaps) **(verify that RetroArch reads a config there and takes no folder from the config file's own place)**. Nano's own launch passes the copy as `CONFIGFILE`. The framework's launch from the home screen passes `<sys.gammaos.retroarch.cfg_dir>/retroarch.cfg` (`kRaCfgDirProp`, `raLaunchConfig`), so the property names `thimsy-launch/` for the whole run, as the next paragraph says, and `NanoRetroArchConfig.java` does not change **(verify that `RootWindowContainer` reads the property at each launch)**. RetroArch's `config_save_on_exit` and its "Save Current Configuration" then write the copy, never the slot, and step 4 takes the changed settings back.

**One owner of `sys.gammaos.retroarch.cfg_dir`.** Today many places set it, all through `NanoMenu::retroarchConfigFile()` (`NanoMenuPS3Folder.cpp` 969-984): the watcher `retroarchConfigWatchStart()` (989ff), which runs in both the home and the overlay process, at every mount change and every 30 s; each home launch just before it starts (`NanoMenuXmb.cpp` 3952 and 4150); Quick Resume's two handoffs (`NanoMenu.cpp` 3704 and 4003); the BIOS installer (`NanoBiosInstall.cpp` 194, 206), the button map (`NanoMenuButtonMap.cpp` 278, 414) and the SD move (`NanoMenuPS3Folder.cpp` 1197, `NanoSdMove.cpp` 2267). Each publishes the slot's folder. One of them running between Nano's launch and `RootWindowContainer`'s read, or during the run, would make RetroArch read the slot. Its saves would then go beside the ROM, hiding the family save for that run and splitting it afterwards; its states would be read beside the ROM, where `savestate_auto_load` can load a shipped build's `.state.auto` of another core (against OA-53); and its loading menus would be shown, so the sweep's guard is gone. So:

- The property gets one writer, a new `raPublishConfigDir()`. It reads the pending-run file under its lock (the file step 3 writes and step 4 clears, shared by the home and the overlay). While a RetroArch launch is pending or running, it publishes the copy's folder, `thimsy-launch/`, never the slot's. Otherwise it publishes the slot's folder.
- `retroarchConfigFile()` only returns the stored live file, which the BIOS installer, the button map and the SD move edit. It calls `raPublishConfigDir()` instead of setting the property itself, and so does the watcher.
- Each home launch (`NanoMenuXmb.cpp` 3952, 4150) and each Quick Resume handoff (`NanoMenu.cpp` 3704, 4003) runs steps 1 to 3 first, which write the pending-run entry, and then publishes. So no call made after step 3 can publish the slot's folder for that run.

**Quick Resume** is a Nano launch like any other. Its handoff passes the per-launch copy (through the property above), and it gets the same step 4 once RetroArch's process ends. The state it resumes from, and the snapshot it writes before the handoff, live in the launch's state folder, `states/{state_core}/{system}/{subdir}/{game}.state.auto`, and its SRAM snapshot in the launch's save folder, not in `/data/system/nano_cache/states/` or beside the ROM (`NanoMenu.cpp` 3440-3447, 3737-3738 look there today) **(verify how RetroArch finds the resumed state when started by the handoff)**. Its snapshots have the game's name, so the sweep leaves them.

The copy-back waits for RetroArch's process to end, not for Nano to come to the front. A new launch while RetroArch is still alive first ends that run and waits for the process to end, then runs that run's step 4, then this launch's steps; **(verify)** the way that lets RetroArch write its saves first (finishing its activity, its `QUIT` network command, or as the last resort a stop as `sdStopIfRunning` does). A crash or a power cut leaves the slot clean and the copy on the device; its copy-back runs at the next start, once no RetroArch process is running. The append route RetroArch's desktop builds have is not used on Android **(verify whether the Android build takes one)**.

So a RetroArch started outside Nano, during a Nano run or after it, reads only stored files, which hold no launch value: this device's set on a card it migrated with, the earlier files on a card with no marker. It saves beside the ROM, as shipped builds and the ES-DE app do today, never into a family or core folder, and its saves are legacy files that §2.7 takes in or lists, never hides. Moving RetroArch's live config to device storage instead is owner question 9.

### 5.7 Which emulator a launch uses

Per launch, first that can run here (`nanoplat::Emulators`): the game's pick in this device's set; the system's pick in this device's set; the image default (W8's seeded store); the system's own emulator (for a game pick that cannot run); a custom system's first catalog emulator (W8-EMU-20 to -22); else "Emulator not installed". A fallback is never recorded (W8, kept). `systems.json`'s launch fields are read only when this device has no pick and no image default for a system (a custom system first seen on this card).

## 6. Migration and the compatibility floor

### 6.1 Android, updating from a shipped build

Run once, on the first start of the build that carries this change. Nothing is deleted.

1. The device id is computed; the local set root and its `device.json` are made.
2. The switch takes its first value from `emu_sd` (§4.6).
3. **Picks:** the local pick files stay as they are, except that `nano_game_emulators.json`'s keys for games under a card's `ROMs/` are rewritten to §2.2's `<card id>/<system>/<rel>`. In store mode, the picks the device actually launches today are folded into them: each game's `<altemulator>`, else its `emulators.json` item, as `esdeStoreLoadGameEmus` resolves them, goes into `nano_game_emulators.json`; each system's `<alternativeEmulator>` adopted today is already in `nano_systems.json`'s launch fields. Labels for emulators that cannot run here are not folded in. The picks as they stand after the fold, every game's and every system's, runnable or not, are also written to `<local set>/legacy-picks.json` and never changed again: §2.7 reads them to know whose a shipped build's save is on a card with no store, since `nano_game_emulators.json` is this device's own pick file from now on.
4. **Settings files:** taken only while the card named by `kEmuSdCardProp` (the card the device adopted, `NanoSdMove.cpp` 1997-1998) is in. Its slot files become the local copies, and each slot gets a marker naming this set. Until then the local `device.json` has `"migration": "slots-pending"`: no slot is filled, the card set stays partial (no `device.json`, §5.5), and launches use the slots as they are, as shipped builds do. A different card in the slot gives nothing: its files are not taken and its slots are not filled. With the emulator folders on internal storage nothing is pending. App-private files are already local.
5. **Switch on, card in, step 4 done:** §4.4 copies the local set to the card.
6. **Theme:** the live theme keys are this device's own values. If the theme card has no `theme.json`, it is written from them. If it has one (another device got there first), it is shown, and the device's own values go to the local theme file. A one-line notice says the theme came from the card.
7. **Playlists:** user playlists in `nano_music.json` are written to `Thimsy/playlists/` on the library's volume (§2.5). A name already taken there is written as `<name> (<model name>).m3u8`. `nano_music.json` keeps each until its file is written, then holds only the scan cache.
8. **Downloaded themes:** each set in `/data/system/nano_esde_themes` (`NanoMenuEsdeMenu.cpp` 197) that the theme card's `ES-DE/themes` lacks is copied there (copied, not moved; skipped when the card lacks room), so a `theme.json` naming it finds it on every device (OA-37). The theme list also reads `<theme card>/ES-DE/themes` when the store is elsewhere.
9. **Saves and states (OA-53):** no bulk step. Saves and states shipped builds left beside the ROMs or loose in RetroArch's folders are copied in game by game, at a launch by the family or core they belong to, and every other one is listed in Older saves (§2.7, owner questions 17 and 18); the originals stay. Shared storage needs no step either: it is already in the emulator folders on the card (`emu_sd` on) or on internal storage (off), and nothing is mirrored.

A device with no settings of its own (a fresh install) meeting a card with legacy shared files (`<emu>/app/`, settings in the card folders) and no set for its id is asked once: "This card has emulator settings from before. Use them on this device?" Yes copies them in as this device's set. This replaces `emuSdForeignDialog` and keeps today's restore-after-reinstall for old cards.

### 6.2 Linux

No Linux build has shipped, so devices need no migration. `linux-next`'s shared-pick code is reworked before it merges (§7). Linux never imports Android's settings files or picks (different emulators). On a card from Android, Linux's set starts from the image defaults. No card has `retroarch/linux/` or `<emu>/linux/`, so Linux starts straight on OA-53's per-core folders (§2.7).

### 6.3 The floor and older builds

- **Additive only.** `devices/`, `theme.json` and the playlists are new files and folders. `format.json` stays at major 1. Shipped builds ignore them: they leave unknown folders alone, and `repoint` rewrites only absent card ids followed by `/emulator_config`, which is right for this card anyway.
- **A card used by both a shipped build and a new build:** the shipped build keeps using and writing the shared legacy files (`<emu>/app/`) and labels; the new build does not read them after migration, so such a change does not reach the new one (owner question 12). The slots are different, since there they are the shipped build's only copy of its RetroArch and PPSSPP settings: on the card the new build migrated with, the slots carry its marker, so a shipped build's edit there is taken into the migrated device's set, and the two keep sharing those files as before; on any other card the slot has no marker, so the shipped build's files are kept and put back after each run (§5.6). No setting is lost either way.
- **Saves on a card shared with a shipped build:** a shipped build still writes every RetroArch save and state beside the ROM, whatever its core, also on the card the new build migrated with, because Nano never writes a launch value into the slot (§5.6). So it keeps finding its own saves, and two shipped builds with different cores can still overwrite each other's file there, as today. New builds never write beside the ROM, so they never overwrite a shipped build's save, and a shipped build never overwrites theirs. A shipped build's newer save for a game a new build has already taken in is listed in Older saves, with a notice at the next launch by that family (§2.7): the save is split until the user picks one, never hidden.
- **The floor** (Q12) is the first Android release with this change. From it, Android behaves as §2 to §5 say. Linux has the behaviour from its first build.
- Legacy files are never cleaned up automatically. A later "Remove old shared settings" action can be considered once every device the owner uses is past the floor.

The libretro core-file name is definition data, not code (OA-54): each libretro launch entry carries `core_file`, a template with `{core}` (RetroArch's `launch.android` entries `{core}_libretro_android.so`, its `launch.linux` entries `{core}_libretro.so`), and `{core.path}` is the cores folder joined with the filled template. `systems.json`'s `coreSo`, which shipped builds write in the Android form, is read through the `frontend: libretro` definition's `launch.android` template to get `{core}`, then matched to this platform's entry by `core`; a device that writes `coreSo` for a system it adds fills the same template. So today's `coreName` rule goes, and the engine names no core-file form. LO.
- `linux/package/thimsy-data` (or each emulator's package): installs the shipped definitions for RetroArch, PPSSPP and ScummVM in `/usr/share/thimsy/emulators/`. LO.
- `nano/platform/linux/` settings dispatcher (W6-caps keyed table): the two new rows. LO.
- `linux/src/thimsy-session`: always publishes `/run/thimsy/unit-serial` at start, from nvmem, empty when there is no chip id (§1); takes a `bind` request for a definition of origin `system` or `index` and releases it when the game's process group ends (§2.7). LO.

## 9. Questions for the owner

1. **The local theme while a card's is shown.** Separate values: the device's own theme comes back when the card leaves (recommended, §4.7, closest to "the card takes priority over the device's local value"). Or a mirror: the device keeps the last theme it showed.
2. **A switch for the card theme.** None: it always applies with a theme card in (recommended). Or a per-device switch like the emulator sets'.
3. **Borderline theme keys.** Recommended: sounds stay local (including `nav_sounds`, although `nano-theme.props` sets it with the theme), and custom wallpaper images stay local. Alternative: a wallpaper image on the library card travels, written `%CARDID%`.
4. **ES-DE app theme edits.** Mirror the four keys to `es_settings.xml` and take the ES-DE app's own theme changes back into `theme.json`, with §2.4's checks against stale rewrites (recommended). Or mirror only.
5. **ES-DE labels.** Never written or adopted after migration, so the ES-DE app and Thimsy keep separate picks (recommended). Or Android keeps writing labels on a pick, so the ES-DE app follows the last Android device's choice.
6. **Turning the switch on when the card already has this device's set.** Ask, with "Use the card's" first when the local set is unchanged since install, else "Use this device's", and keep the replaced copy once in `.previous` (recommended). Or follow OA-46 literally and copy the local set over with no question (the copy is still kept).
7. **Copying another device's set.** A manual Settings action for same-platform sets (recommended). Or also offer it automatically to a new unit of the same model.
8. **The id on the card.** The platform and a hash of the serial (recommended, §1); the model label is in `device.json`, not in the id. Or the raw serial, easier to match by hand but personal data on a card that may be lent.
9. **RetroArch's live config on Android.** A slot in its card folder, filled before each launch, with each Nano launch passing a per-launch copy that alone holds the launch values (recommended for v1: no framework change, §5.6). Or move it to device storage, which changes `raLaunchConfig` and the framework's `NanoRetroArchConfig.java`, and stops RetroArch launched outside Nano from reading another device's settings.
10. **Switch defaults.** Linux on; Android from `emu_sd` (recommended).
11. **Clashes.** File-level, the card wins (OA-46), and the losing device copy is kept once in `conflicts/` (recommended). Or no copy kept.
12. **Cards shared with shipped Android builds.** Their changes to the old shared files (`<emu>/app/`, labels) are not seen by new builds after migration; slot files stay shared with the migrated device, and are kept and put back on other cards (§6.3) (recommended: accept and document). Or keep importing the shared files, which brings back the shared model for those devices.
13. **Save states.** Answered by OA-53: shared on the card by every device and both platforms, one folder per core (§2.7).
14. **Scraper preferences.** Local only: neither adopted from nor written to the card's `es_settings.xml` (recommended, §2.6, OA-47). Or keep writing them (never adopting), so the ES-DE app scrapes the way the last device that changed one does.
15. **`systems.json`'s shared fields** (which systems show, their order and names, custom systems). OA-46 now names the launch fields as per device; the other fields choose no emulator, so they stay library data on the card, card wins, as today, and a custom system shares its entry but not its launch fields (recommended, §2.6, OA-49). Or local per device, which needs a local layer over the card's list.
16. **Switch off, card holds this device's set.** Ignore the card set (recommended, §4.1: a read-only set would drop every edit at the next start). Or use it read-only, as OA-46's lookup sentence alone suggests.
17. **Where RetroArch saves live.** A fixed folder per save family and system, `retroarch/saves/<family>/<system>/`, set by the launching core's definition. Saves made elsewhere (beside the ROM, loose or in RetroArch's per-core folders) are copied in once per game for the family they belong to (the core-sorted folder's core, else the game's legacy pick, else the system's), and every other one is listed in Game Options > Older saves; Nano writes no launch value into the slot, so shipped builds keep saving beside the ROM (recommended, §2.7: no later change of picks or launch fields can move, hide or overwrite a save). Or keep saves beside the ROM for one family recorded per system on the card the first time it is decided: shipped builds would keep seeing new builds' saves, but a new card file, and a shipped build's re-pick could still write an incompatible core's save there.
18. **Save states shipped builds left beside the ROM or in `retroarch/states/`.** Copy each into `retroarch/states/<core>/<system>/` at a launch by the core it belongs to, list the rest in Older saves, and leave the originals (recommended, §2.7). Or leave them only: new builds' RetroArch no longer lists them.
19. **Shared storage while Android's emulator files are on internal storage** (`emu_sd` off). It stays there until the user runs Move Emulator Files, as today (recommended, §2.7). Or move it to the card on its own when a card is in, as OA-52 and OA-53 read literally suggest, at the cost of a large copy nobody asked for.
20. **Card out, shared storage on the card.** The emulator does not start until the card is back (recommended, §2.7: no mirror). Or usb_storage_plan.md's fallback to an internal folder, which is the second copy OA-52 and OA-53 rule out and can split a save.
21. **User definitions on the card.** A copy in this device's set, with a changed copy used only after the device's import screen accepts it (recommended, §2.8). Or local only, imported again by hand after a reinstall.
22. **PortMaster's space on RK3566 (OA-50).** `/storage` is 256 MiB (`linux/board/rk3566/genimage.cfg`, entry 4), and PortMaster's runtimes are hundreds of MB, the popular set 614.5 MB (`docs/linux/research/portmaster.md` §5 and Q7). Recommended: a dedicated local ext4 partition that D60firstboot makes at first boot between `info` and `games` (4 GiB *(guess)*, or a share of the card capped at that), mounted at `/storage/ports`. The image stays 2410 MiB, so writing a card stays quick, and `/storage` keeps its size. It moves the games partition's start, so the re-adoption of an old library must look past it; no Linux card has shipped, so nothing migrates. Or grow `data` in `genimage.cfg` (for example to 4 GiB): one line, but the image and every card write grow by the same amount. Or keep 256 MiB and offer only ports without large runtimes.
23. **Pointing on Linux.** A key in the emulator's settings where it has one, else a symbolic link on `/storage` to the card folder, and a bind mount only for an emulator that refuses links (recommended, §2.7). Or bind mounts throughout, as `LIBRARY-FORMAT.md` 4.18 drafted for PPSSPP, which needs a root step at every launch.
24. **MAME's `cfg/`.** Shared with the rest of `mame/` in the family folder, with pad controls per device in RetroArch's remaps (recommended, §2.7: no definition can keep a folder inside a shared folder per device, and the cores have no option for `cfg/` alone **(verify)**). Or per device, which needs a core option that moves `cfg/`, or a new definition field for a settings folder inside shared storage.
25. **A save of another family beside the ROM.** Listed in Older saves, copied in only by hand, with the current save kept as `.bak` (recommended, §2.7). Or never offered: safer for a core that misreads another's file, but the save is then out of sight.
26. **RetroArch's loading menus during a Nano launch.** This is a change in behaviour: today a user can load another core or game from RetroArch's menu after a Nano launch. Recommended: hide Load Core, Load Content, Load Disc, History, Favorites, the playlists and Explore for the run, put them back after it, and sweep another game's files out of the launch's folders after the run (§2.7). Without the hidden menus, the same game under another family's core can overwrite the family's save, and the sweep cannot catch that. Or leave the menus and keep only the sweep, accepting that risk. Or use RetroArch's kiosk mode, which also hides its settings.
27. **A core whose states or saves fail the cross-platform test** (`linux_handheld_plan.md` question 11; OA-21's save round trip). Recommended: a distinct state folder for its Linux build (`state_core` in its Linux launch entry, §2.7), so the two builds never meet; that core's states then do not travel between platforms. Or keep the folder shared with a stamp per state and no auto-load on a mismatch: states stay visible on both sides, but a wrong manual load can still crash the core. A core whose in-game saves fail OA-21's round trip gets its own `save_family` on Linux, with no alternative: one save file cannot carry a stamp.
28. **Games of one name in subfolders of one system.** Recommended: a `{subdir}` level below the system folder in the save and state paths (§2.7), empty for a game directly in `ROMs/<system>/`, so `USA/Game.sfc` and `Europe/Game.sfc` keep two saves. Its costs: a core that keeps one file for every game (Sega CD's `scd_U.brm`) keeps one per subfolder, and a game moved to another subfolder finds its old save only through Older saves. Or no subfolder level, with a warning when two games of one name share a system: one folder per system, but those games still write one file.
